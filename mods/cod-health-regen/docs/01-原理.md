# 原理与偏移

## 1. 为什么这样做

需求是"类 CoD 的呼吸回血"：受伤后停一段时间开始回血，回满即止。能做到这件事的地方只有三处：

| 方案 | 结论 |
| --- | --- |
| 改 UnrealScript / 打 upk 补丁 | 要动 `SFGame.upk`，破坏客户端的包哈希与发布校验，且回血是逐帧逻辑，脚本改起来还要重编译包。**没选** |
| 服务端（`local-server/`） | 对战是客户端原生逻辑，服务端不管每帧血量。**不可行** |
| 进程内读写内存（本 mod） | 只碰 `Pawn.Health` 一个 int，不动任何文件。**采用** |

与 `corpse-flinch` 相比，本 mod 更进一步：它**不安装 ProcessEvent 钩子**。因为回血只是"改一个整数字段"，不需要请游戏执行任何函数，所以不需要主线程、不需要远程分配、不与任何已经挂了桥的 AI worker 抢 `0x6008D0`。这使得它与 `corpse-flinch`、AI worker 可以同时存在。

## 2. 数据在哪

客户端自带的运行时负责版本锁定：

- `runtime\tools\local_battle_bridge.py` 的 `Bridge`/`Reader` 会用 **sf2.exe 的 SHA-256**（`start_local_client.EXE_HASH`）校验磁盘上的客户端，并拒绝连接任何不是这个 EXE 的进程。客户端一更新就报错，绝不会写进错的地方。
- 下面的绝对地址只在当前客户端成立，**不要**在版本变化后沿用：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `GWORLD` | `0x179B2F4` | 当前 `UWorld*` |
| `UWorld.PersistentLevel` | `0x50` | 持久关卡 |
| `ULevel.Actors` | `0x3C` | 关卡 actor 数组（TArray） |
| `AController.Pawn` | `0x228` | 控制器当前 pawn |
| `APlayerController.Player` | `0x3D4` | 只有**真人**控制器非空 |
| `UObject.Class` | `0x34` | 经 `Reader.header()[13]` 取类名 |
| `UProperty.Offset` | `0x64` | 属性在对象内的存储偏移 |

## 3. 两个关键偏移是运行时解析的

`Health` / `HealthMax` 的存储位置**没有写死**。`sf2mod/game.py` 的 `Fields` 在连接后遍历 `GObjects`，挑出 `IntProperty`、名为 `Health`/`HealthMax`、且 `path()` 正好是 `Engine.Pawn.Health` / `Engine.Pawn.HealthMax` 的属性对象，再从 `+0x64` 读出真实偏移。找不到就直接报错退出，不猜。

这是对"兼容性"最实际的一条：客户端重编译后属性偏移变了，本 mod 仍然能自己找回来。

（包内静态核对过：`Engine.upk` 里 `Pawn.Health`、`Pawn.HealthMax` 都是 `IntProperty`；`Pawn.HealDamage(Amount:int, Healer:object, DamageType:class)` 存在，但本 mod 不用它。）

## 4. 只认本地玩家

在关卡 actor 列表里找 `*PlayerController` 且 `Player != 0` 的控制器，取它的 `Pawn`。离线单人环境下只有本地玩家满足这个条件：AI 控制器（英雄 bot、训练 bot）没有 `Player`。

拿到后缓存 controller+pawn，每 tick 只用两次读确认还指向同一个 pawn；世界/关卡变了就清缓存与类名缓存（地址会被回收复用）。

## 5. 回血规则

`sf2mod/regen.py` 是纯逻辑，离线单测覆盖：

1. 血量下降 ⇒ 记受伤时刻，清空累积；
2. 距上次受伤 `< regen_delay_seconds` ⇒ 不写；
3. 过了延迟 ⇒ 按 `regen_per_second × 实际经过时间` 累积，够 1 点才写一次整数；
4. 永远 `min(写入值, HealthMax)`，且只增不减；
5. `Health <= 0` ⇒ 什么都不做（不复活）；
6. 读数不合理（`HealthMax <= 0`、`HealthMax > 100000`、`Health > HealthMax`）⇒ 不写，宁可不动；
7. 自己写上去的血量不会被下一 tick 误判成"受伤"；
8. 单次 tick 的最大累加时长按 0.5 s 截断，游戏暂停/卡顿后不会一次性跳满。

## 6. 验证状态

实机（开发客户端，`doctor`/`verify` 全绿）：

- 已验证：连接、EXE 哈希校验、**四个偏移全部由实时反射解析**（`Health=0x338`、`HealthMax=0x33c`、`Controller.Pawn=0x228`、`PlayerController.Player=0x3d4`），后两个与 corpse-flinch 的硬编码值独立吻合；菜单世界下"找到控制器但 pawn 不可用"判定正确；worker 主循环无异常；关游戏后 `game-exit` 自行退出；无残留进程。
- **已验证（2026-10-25，1.0.2，用户实机对局）**：扣血 → 停 4 秒 → 回满。日志节选（`logs/health-regen-20261025.jsonl`，game pid 13020）：

| 事件 | 血量 | 说明 |
| --- | --- | --- |
| `damage` | 76/100 | 被打 |
| `regen` | 78/100 | 距上次受伤 **4.02 s**（配置 4.0） |
| `full` | 100/100 | 回满 |
| `damage` | 71/100 | 第二次 |
| `regen` | 73 → 98 | 同样是 4.02 s 后开始 |
| `full` | 100/100 | 回满 |

  同一次运行里 `names` 事件从 27835 一路涨到 116198（每次换图继续涨），直接印证 §6.3 的根因：attach 时读到的名字表只有最终长度的约 1/4。

### 6.1 为什么 1.0.0 "什么都没发生"

**不是偏移错。** 1.0.1 的反射把四个偏移都解出来，两个控制器偏移与 corpse-flinch 的硬编码一致，而 corpse-flinch 在同一份 EXE（相同 hash）上是能用的——它的日志里有 6 次 `drag-start`，那需要 `Player.pawn()`。

真正的问题是失败路径被我写成**静默**的，外加几处判据不严：

| 缺陷 | 后果 | 1.0.1 的做法 |
| --- | --- | --- |
| `except OSError: pass` | 读失败 165 秒也不留一行日志，看起来就是"没生效" | 记 `read-error`（首次 + 每分钟一条） |
| 找到控制器但没 pawn（阵亡/换图/菜单）就 `return 0` | 永远走不到 GObjects 兜底 | 没有可用 pawn 就继续找，兜底每 3 秒一次 |
| 把"没有 pawn 的控制器"缓存后直接返回 | 一旦缓存到错误对象就永久卡死 | 只把"有可用 pawn"当作命中 |
| 不校验 `HealthMax` | 菜单里的 limbo pawn（实测 `Health=0, HealthMax=0`）会被当成玩家，整个 mod 变空转 | `HealthMax` 不合理即拒绝（`_usable`） |
| 关卡 actor 列表只用 `Player != 0` 认玩家 | 实测 26 个菜单 actor 里有 **9 个**在 `Player` 偏移上恰好是非零指针 | 恢复 `*PlayerController` 类名判据 + `Player != 0` |
| 无法自证 | 失败时只能靠猜 | `no-pawn` 每 30 秒报 world/level/actor 数/候选控制器 |

补充实测：GObjects 全量扫描是 **0.16 秒 / 164k 对象**，所以它可以当常规兜底，而不是"最后手段"。

### 6.2 启动期连上会踩缓存坑（1.0.0 的第二个真 bug）

第一次用 `tools/launch.py` 起 worker 时，日志停在：

```
waiting-boot  Unexpected object array
waiting-boot  客户端缺少属性：Engine.Pawn.Health, Engine.Pawn.HealthMax
fatal         客户端缺少属性：Engine.Pawn.Health, Engine.Pawn.HealthMax
```

而**同一个客户端**上另开一个全新进程却能立刻解析出偏移。根因不在"客户端还没加载完"，而在缓存：

- `Reader` 在 `__init__` 里只读一次名字表；启动早期读到的是**较短**的表。
- `Reader.header()` / `Reader.path()` 是 `@lru_cache`，按**地址**缓存。启动期扫描会把"名字还没加载"的地址缓存成错误路径，之后**永远不会自愈**。
- 客户端自带的 `NativeAPI.refresh()` 正是每次都清这两个缓存，所以它是安全的。

修法：`refresh_names()` 在每次解析前重读名字表并清两个缓存。改完后同一场景从"300 秒仍失败"变成"3 秒成功"。

### 6.3 为什么进了地图就认不到玩家（真根因，1.0.2）

用户在 1.0.1 的对局日志（`no-pawn` 诊断）给出了决定性对比：

| 场景 | world | actors | human_controllers | candidates |
| --- | --- | --- | --- | --- |
| 菜单 | 0x50bdb980 | 26 | 1 | `SFEntryPlayerController` |
| **进入地图** | 0x50bd0380 | **244** | **0** | **`[]`** |
| 回到菜单 | — | 26 | 1 | `SFEntryPlayerController` |

真实对局不可能没有玩家控制器。菜单能认、进图全瞎，说明**类名读不出来**：

- `Reader` 的名字表在 `__init__` 里只读一次；加载地图会在名字表里**追加**新名字（本机实测：菜单 108k~109k 条）。
- 名字索引一旦超过 attach 时的长度，`name(index)` 返回 `'<bad-name:N>'`；于是 `*PlayerController` 类名判据对所有对象都不成立 → 关卡 actor 列表和 GObjects 扫描都认不出控制器。
- 三个 lru_cache（`name` / `header` / `path`）都会把这个错误结果**记住**，不主动清就永远不恢复——1.0.1 的 `refresh_names()` 只清了 `header`/`path`，**漏了 `name`**，所以进图后照样坏。

已在实机上复现并验证修复（把内存里的名字表截断成 100 条来模拟 attach 过早）：

```
real name table: 109268
class (fresh) : 'SFEntryPlayerController'
truncated to  : 100
class now     : '<bad-name:6912>'          <- 正是进图后的症状
find()        : 0x0
name table repaired to : 109268
class after   : 'SFEntryPlayerController'  <- 修好
```

1.0.2 的三层修复：

1. `refresh_names()` 里补上 `bridge.name.cache_clear()`；并在**每次重扫**（含换地图时立即触发）前重读名字表。
2. 新增**完全不依赖类名**的兜底：关卡 actor 中 `Player != 0` 且它的 `Pawn` 是本关卡 actor、`HealthMax` 合理 → 认作本地玩家（`via='level-no-name'`）。
3. `no-pawn` 诊断新增 `names`（名字表长度）与 `sample_classes`（关卡前 8 个 actor 的类名）：如果类名是 `'<bad-name:…>'`，一眼就能看出是名字表问题。
