# 07 · 版本历史

按时间顺序。每条都写"改了什么"和**为什么改** —— 后者比前者重要：大部分版本是在证伪一个错误假设。

当前版本：**1.10.4**（修「崩溃后启动器不动」；功能代码与 1.9.3 一致）。

## 1.11.1 — 让位名单补上异形 PVE（2026-10-26）

**改了什么**：`ai_priority` 的让位判据新增 `sfsurvivalgame` / `sfdefencegame`（异形 PVE 的生存/防守局），
前缀直接从客户端自己的 `local_pve_allies.GAME_PREFIXES` 读，读不到才用内置常量；
顺带把团队死亡也补上 `sfteamdeathgame`（原来只认 `sfaiteamdeathgame`）。

**为什么**：1.11.0 只让出了爆破/夺取/逃脱/死亡/英雄/路线图团队死亡，**漏了异形 PVE**。
而 R6 的 PVE 人机队友（`local_pve_allies`）同样要先拿到 `0x6008D0` 才能跑，所以开着鞭尸进 PVE 时：
`local-route-watch` 装不上桥 → 每秒 `Route bridge session mismatch` → **人机队友一个都不生成**。
玩家选项 `pve.allies` 本身是生效的（离线核对：`bots.pve_allies.enabled = true, count = 3`），
模块要用到的 `SFGameInfo.SpawnManager` / `SFAISpawnManager.SpawnInstantAI` / `SFAIController_Rifleman`
在当前客户端包里也都存在，所以问题只在让位名单。

## 1.11.2 — 让位名单补上刀战房（2026-10-26）

**改了什么**：`ai_priority` 的判据再新增一条——当前对局的 `CustomModeType == 5`（刀战房）时让出入口。
读法和客户端的 `KnifeRule.read_rule` 完全一致：先 `SFGameInfo.CustomModeType`，取不到再读
`SFGameReplicationInfo.CustomModeType`。

**为什么**：刀战不是一种"游戏类"，它只是团队死亡局上的一个房间规则，所以 1.11.1 的类名前缀判据看不到它。
而**只有 `local_route_worker`（路线/boost 两条 TDM 路径）会执行刀战规则**——`local_hero_worker` 和
`local_pve_allies` 里一处 `KnifeRule` 都没有。实测现场：R7 的 `runtime/evidence/local-boost-status.json`
写着 `"knife_rule": true, "grenades_enabled": false`，但 `"elapsed": 0.0, "stats": {}` —— 规则认对了，
worker 却一帧都没跑，因为入口被本 mod 占着。规则再正确，没人执行也等于零。

**注意**：英雄模式和异形 PVE 里的刀战房本来就没有分工逻辑（那两个 worker 不认刀），不在本 mod 能修的范围。

**实机验收（2026-10-26，用户）**：刀战房机器人正常掏刀。日志证据（1.11.2）：
`ai-priority released knife:sfaiteamdeathgame_0` → `bridge-foreign`（AI 已接管）→ 离开房间后 `ai-priority owned free-play`。
旁证：`runtime/evidence/local-boost-status.json` 在**房间进行中**会显示 `elapsed > 0`；但**对局结束那一刻**，
boost worker 会被重新调用一次并在第一帧写回 `elapsed: 0.0`（`GameMatchInProgress` 判据为 false 时先写状态再 break），
所以对局结束后去看这个文件永远是 0.0 —— 它是可观测性缺陷，不是没跑。判断是否生效请以 corpse-flinch 日志的
`released knife:*` 和画面为准。

## 1.0.0 · 首个可分发版本

命中判定从"射线 + 骨骼距离"改为**读武器自己的命中记录** `RifleHitResult`（`docs\02` §3），冲量标定 700 / 上限 1200。

为什么：射线近似有两个不可修的毛病——打尸体旁边的墙/地面会推尸体（假阳性），擦着躯干边缘又判成没中（假阴性）。而游戏本来就算好了命中 actor 与命中点，只是伤害链在"已死亡"处分叉了。

## 1.1.0 · 弓与近战

- 弓：读投射物飞行折线
- 近战：读 `SFPawn.DoingExigencyAttack` 状态位

为什么：两者的命中都不进枪的命中表；但它们各自有"游戏自己算过"的痕迹（折线、状态位）。

## 1.2.0 · 投掷武器

支持飞斧等投掷武器，同时修两个 bug：

1. `try: self.melee(); self.arrows()` —— 近战读 pawn 时抛 `OSError` 会把**投射物检测整段跳过**。改成两个探测器各自 `try`。
2. 推力方向压平到水平面（尸体躺地上，沿投射物速度（朝下）推只会压进地板，实测位移只有 2.09 / 7.69 cm）。

还加了 `plausible()`：手里不是子弹类武器时，命中表那片内存是无关数据（`actor=0` 或坐标是天文数字），不再当真。

## 1.3.0 · 投射物判据重写

命中 = 投掷物**在尸体旁被销毁**（默认 45 cm）。

为什么：1.2.0 用"整条折线 + 14 cm"，而 14 cm 是从贴脸投掷标定的；正常距离投掷时最近骨骼常在 30~70 cm，导致真实命中被漏掉。

## 1.3.1 · 采样阈值与缓存

- 点与点之间允许的位移改成按实际间隔算（12 000 单位/秒 × dt）；此前写死 400 单位，检测循环一慢就把真实轨迹整段丢掉。
- 换图时清掉类名缓存。

## 1.4.0 · 寿命 + 整条轨迹

实测：命中尸体的投掷物 0.87~1.08 秒就消失（在空中解体），落地的那把活了 17 秒。于是判据变成"寿命短 + 折线靠近尸体"，距离阈值放宽到 60 cm（只用来排除"从旁边几十厘米飞过去"）。

## 1.5.0 · `bHidden` 实验（被证伪）

假设：命中时游戏会立刻隐藏投掷物（`Engine.Actor.bHidden`，偏移 0xB0、掩码 0x2）。

实测：翻转发生时投掷物离最近骨骼 **1522.5 / 1550.7 / 1651.9 / 1718.7 cm** —— 它是**飞出地图**才被隐藏的。假设推翻。

## 1.6.0 · 回退 + 性能

- `bHidden` 降级为只记日志（`projectile-hide`），判据回到整条轨迹
- 尸体骨骼加 250 ms 缓存（`BONE_TTL = 0.25`）。此前每个采样点都重读 70 根骨（70 次跨进程调用），循环只有几 Hz，轨迹粗到无法判定
- `Projectiles(samples=512)`（原 64），覆盖 2 秒飞行

## 1.6.1 · 半径标定

`projectile_radius` 60 → **70**：五次实测里唯一没推动的那次距离是 63.2 cm（飞斧模型本身在旋转，接触范围比骨球大）。

## 1.7.0 · 边飞边判

- 投掷物改成**每飞出一段就判一次**，命中当帧 `AddImpulse`；此前要等对象被释放才结算，白等约 1 秒
- 投掷力度 700 → **900**，`max_impulse` 1200 → 1400

为什么：用户反馈"延迟过高"。延迟的根因不是轮询慢，而是判据要等"销毁"这个事件。

## 1.8.0 · 力度

投掷力度 900 → **1080**（+20%），`max_impulse` 1800。

## 1.8.1 · 投射物"隐形"

修：actor 地址被复用 ⇒ 类名缓存说谎 ⇒ 新的投掷物在检测循环里根本不出现。新出现的地址一律重读类名。

同时加 0.12 s 起飞宽限（站在尸体上投掷时出生点离骨骼只有 30 cm，会被误判），新增 `projectile-spawn` / `projectile-lost`，`status` 增 `loop_ms`。

## 1.8.2 · 投掷武器左键近战

这个动作没有专属状态位，靠 `SFWeapon.BurstFireCount`（0xBE0，每次开火/挥砍 0 → -1 → 0）的上升沿识别，再等 0.3 s 看弹药有没有减少来和投掷区分（挥砍不减弹药）；0.45 s 去重。投掷半径 45 → 70 cm（实测对准尸体投掷时最近骨骼 60.9~63.9 cm）。

## 1.8.3 · 投掷延迟到当帧

1.8.1 的"起飞后 0.12 s 不算"按 24 m/s 算是近 3 米飞行，**近距离投掷的整个接触段被吞掉**，冲量只能等飞斧落地停稳才施加。改成只丢一个采样（`projectile_grace` 0.02）+ 头 0.15 s 内只认前方尸体（`(骨骼−出手点)·线段方向 > 0`）继续挡住"站在尸体上投掷"的误判。

## 1.9.0 · E 键拖拽

按交互键抓住准星最近的尸体骨骼，再按一下放开。按"还差多远、当前多快"算冲量，最高 400 cm/s，600 cm 自动松手；按键优先读游戏的 `bPressingUsedKey`（0x690，掩码 0x40，跟着改键走、聊天框不误触），读不到才退回 `GetAsyncKeyState`。

## 1.9.1 · 拖拽重写

用户反馈两件事：**异常抽动（鬼畜）**，**视角向上时尸体不跟着抬**。

根因：

1. 旧 `step()` 每个 4 ms 轮询都发一次冲量，`push = clamp(gain*gap - along, ±1200)` 在 140 cm 误差下**每 tick 都打满上限** ⇒ 250 Hz 的饱和 bang-bang，物理引擎来不及积分
2. 目标点是"玩家脚点 + **压平**的水平朝向 × 140 cm，z 固定为抓取时高度" ⇒ 抬头时目标点根本不上升

改法：

- 目标 = **相机眼位 + forward × 200 cm**（三维，抬头即抬）
- 控制频率 250 Hz → **60 Hz**（中间让物理积分）
- **临界阻尼 PD**：`accel = kp*error − kd*velocity`，`kd = 2*sqrt(kp)`；另加重力补偿（加在限速之后，否则会被速度上限削掉）
- 单次冲量 1200 → 900；速度用 0.5 低通；质量在线学习 `|J|/|Δv|`
- `too-far` 改为持续 0.3 s 才松手

## 1.9.2 · 抓骨盆

你看到的：抓头会把尸体甩出 714 cm、1.9 秒就松手。

为什么：头/手在质心之外，同样的冲量几乎全变成力矩。改抓 `Bip01-Pelvis`（按名字找并缓存），稳定在误差 30~60 cm、单次冲量 130~430。质量学习加"单样本最多改 15%"（之前会在 9~20 kg 之间跳）。

## 1.9.3 · 修致命崩溃

`toggle_drag` 里 `aim` 未定义 —— **第一次按 E 就把 worker 打崩**（日志末尾 `NameError: name 'aim' is not defined`）。

同时给拖拽与两个探测器加兜底：非 `OSError` 的异常记一条 `worker-error` 后继续跑，不让一个 bug 结束整局。

## 1.10.1 · 修「装完没反应」（社区反馈）

症状：卸载一次再重装、或者第一次装完就双击启动器 —— 什么都没发生：没有窗口、日志不加一行、游戏里也没反应。

根因（`logs\launcher.log` 只有一句 `worker 启动后立刻退出了（exit 120）`）：
`启动-鞭尸模式.cmd` → `pythonw.exe tools\launch.py` → 再 spawn 一个 `pythonw.exe corpse_flinch.py`。第二层 pythonw **继承了父进程已经失效的 std 句柄**：Python 照样造得出 `sys.stdout`，但每次写都抛 `OSError: [Errno 22] Invalid argument`。`ensure_streams()` 只在 `is None` 时替换流，于是 `make_logger.emit` 里第一行 `print(...)` 就把 worker 打死；解释器退出时再 flush 一次失败，退出码变成 120。

为什么以前"有时候能用"：从有控制台的 `python.exe` 或命令行启动时 std 句柄是好的，只有双击这条路全坏 —— 而双击正是所有人默认的用法。这也是"卸载后重装就失效"的关键：重装本身没问题，是重装后必然要走的那条启动路径坏了。

修复：

- `corpse_flinch.py`：用 `stream_ok()` 探针（`write('')` + `flush()` 实测）取代 `is None` 判断；坏了就换 `logs\worker-console.log`，连它都打不开就换 `os.devnull`
- `tools\launch.py`：给 worker 显式传 `stdout=DEVNULL, stderr=logs\worker-console.log`（双保险）
- `tools\launch.py`：worker 起来后等 2 秒 `poll()`，真死了就弹窗并指向日志，不再静默退出
- `logs\crash.log`：最外层包 `BaseException`，没有控制台也能留下 traceback
- `logs\launcher.log`：启动器每一步都留痕（时间戳 + 中文说明），供排错

顺带修掉三个"装不上"：

- 解压多一层（`mods\corpse-flinch-1.10.1\`）时 `安装.cmd` 直接拒绝。现在改为向上找游戏目录、找不到就弹目录选择框；`tools\install.py` 装完逐项校验文件，缺一个就报错而不是假装成功
- `logs` 被同名文件占用时 worker 启动即死（`FileExistsError: [WinError 183]`）
- 卸载时 worker 还活着、或文档正被 Obsidian 打开：现在先按 `logs\worker.pid` 停 worker；删不掉就明确说"哪个目录被占用、关掉 Obsidian/编辑器再来"

新增：`安装.cmd` 装完会问"现在就把鞭尸挂上吗"，回车即启动，随后打印 worker PID（`--no-start` 可关掉这一步）；`安装.cmd` 不再要求补丁必须已经在游戏目录里。

## 1.10.2 · 修「重装后仍然没反应」：启动器自己开游戏引发的挂载竞态

症状：1.10.1 装好后双击启动器，仍然什么都没发生。`logs\corpse-flinch-*.jsonl` 里只有两行：

```json
{"event": "process", "pid": 14184}
{"event": "fatal", "reason": "ValueError: Unexpected object array"}
```

没有 `ready`，worker 一秒后就退出了。而同一个包装在**已经开着的游戏**上手动跑，立刻就能挂上。

根因：1.10.1 起安装器与启动器会**自己启动游戏**，于是 worker 在 `sf2.exe` 刚创建进程、还没加载完地图时就去 attach：

- 第一步 `Reader.objects()` 读固定地址的 UObject 数组（`inspect_battle_runtime.py:94`），此时数组还是空的 → `ValueError: Unexpected object array`
- 再晚一两秒 → `RuntimeError: Battle API incomplete: 4 functions, 0 controllers`（`local_battle_bridge.py:117`）：桥的 trampoline 必须找到活着的 `PlayerController` 才能装

旧代码把这两种都当致命错误，于是 `fatal` 退出。以前"能用"是因为用户先手动开好游戏、再双击启动器，游戏早就加载完了 —— 这个竞态是 1.10.1 的改动带出来的。

修复（`corpse_flinch.py` 新增 `connect_when_booted()`）：

- 挂载失败不再致命，最多等 **1 小时**（`BOOT_GRACE = 3600.0`），退避 2→5 s 重试
- 日志节流：同一错误每分钟一行 `waiting-boot`（带 `attempts` / `waited` / `retry_in`），错误变化时立刻记
- 挂上时若重试过，先记 `{"event": "booted", "attempts": N, "waited": 秒}` 再 `ready`
- 只有超过 1 小时才 `boot-timeout` 报错退出
- `connect()` 每轮都会打一行 `process`，改成每轮只记一次

为什么值得这样等：桥的 trampoline 一旦装进这个进程就一直有效（`install()` 首行要求入口仍是原始字节），所以同一局里重启 worker 会直接 attach；只有全新进程的第一次必须等游戏加载完。

同版本顺手修的两个安装链问题（测试时踩到）：

- `tools\install.py` 的 `worker_pids()` 原来只要命令行里有 `corpse_flinch.py` 就杀 —— 两份安装并存时（第二个游戏目录、测试目录、备份恢复）会互相误杀。现在要求命令行里同时含**本份安装自己的路径**（`str(Path(dest).resolve()).casefold()`）。
- `tools\uninstall.py` 删不掉时不再直接退出：先列清剩了什么，再问"关掉打开它的程序后按回车重试，输入 n 放弃"（最多 3 轮）。被 Obsidian 当 vault 打开的 `docs\` 是唯一常见的长占用，光靠 20×0.2 s 重试等不到。

## 1.10.3 · 修「双击启动器没反应」：陈旧 worker 把整次双击吞掉了

症状：功能明明能用（日志里 `corpse-hit`、`drag-end` 都在），关掉游戏后双击 `启动-鞭尸模式.cmd`，**游戏不启动、worker 也不起**，什么都不发生。`logs\launcher.log` 里连续几次双击只有两行：

```
12:10:35 launcher 启动 here=...\tools
12:10:35 游戏目录 game=E:\SF2-Offline-20261016
12:10:35 worker 已经在跑，不重复启动 pid=93148
```

没有 `启动游戏`，说明启动器在"开游戏"之前就 return 了。而 93148 是上一次会话留下的 worker：游戏 12:06 关掉以后它并没有退出，还在空转。

根因两条，叠在一起才致命：

1. `tools\launch.py:148` 的顺序错了 —— "已有 worker 就 `return 0`" 排在 "游戏没开就 `start_game()`" **前面**。只要 `logs\worker.pid` 里的进程还活着，启动器就认定"一切就绪"，既不启动游戏也不重挂 worker。
2. worker 不知道游戏已经关了。桥从死进程的内存里照样读得出（不报错），`status.loop_ms` 只是掉到 `0.0`，而 `idle-exit` 要**1 小时无武器**才触发 —— 于是这个 worker 一直占着 `worker.pid`，把后面每一次双击都挡掉。

修复：

- `tools\launch.py`：先确认游戏进程（不在就 `start_game()`，最多等 15 s 看到 pid）→ 再决定 worker。启动器现在永远会把游戏打开，"没反应"这一类不会再出现。
- `sf2mod\attach.py` 新增 `pid_alive(pid)`（`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetExitCodeProcess == 259`）。
- `corpse_flinch.py` 的 `Worker` 记住 `self.pid`（**游戏**进程，取自 `bridge.pid`），`run()` 里每秒检查一次：游戏没了就记 `{"event": "game-exit", "pid": N}` 并立刻退出，`finally` 照常删 `worker.pid`。以后关游戏 = worker 自己走，不会再有陈旧 worker。
- 启动器遇到"worker 活着、但它 jsonl 里挂的是另一个游戏 pid"时，直接 `TerminateProcess` 再挂新的（日志 `旧 worker 挂的是上一个游戏进程，换掉它`）；无法判断时先等 3 秒让它自己 `game-exit`。

打包改动（同一版）：zip 顶层从 `corpse-flinch/` 改成 `mods/corpse-flinch/`（`tools\build_manifest.py` 的 `PREFIX = Path('mods') / 'corpse-flinch'`）。现在**解压到游戏根目录**即可，不用手建 `mods` 文件夹，也不会解成 `mods\mods\corpse-flinch`。

## 1.10.4 · 崩溃之后启动器像坏了一样：残留进程只剩一个 Fatal error 框

症状：游戏自己崩了（或关窗口后崩），屏幕上留着 UE3 的 `Fatal error!` 框（标题是 `Message`）；这时双击 `启动-鞭尸模式.cmd`，`launcher.log` 只有两行：

```
12:20:14 游戏已经在运行 pid=92108
12:20:17 worker 已经在跑，不重复启动 pid=77852
```

游戏不重开、worker 也不换，看起来"启动器又坏了"。其实 92108 就是那个已经崩掉的进程：游戏主窗口早就关了，只剩一个错误框在等用户点"确定"，`client_pid()` 照样找得到它。

崩溃本身跟补丁无关，报告全都指向游戏自己的 `sf2.exe` / `D3D9Drv`：

- `12:20:07 GameViewport == NULL!!! All Windows Closed`（PlayTime 2.6 min，退出/关窗口阶段），`12:20:18` 才轮到 `Fatal error!`；
- `12:25:51 D3D9Device.cpp:893 with error D3DERR_INVALIDCALL`（PlayTime 0.5 min，**加载阶段**），地址 `0x4721e1`/`0x498377`，与 `11:16:52` 那次逐字相同；
- 更早的 `03:07:55 Ran out of virtual memory. ... Request 65536. LastError 8.`（PlayTime 30.4 min，32 位客户端 4 GB 上限）与 `10:52:50 GameViewport == NULL`。

修复：

- `tools\launch.py` 新增 `windows_of(pid)`（`EnumWindows` + `GetWindowThreadProcessId` + `IsWindowVisible` + `GetWindowTextW`），列出某进程所有可见顶层窗口的标题。
- 游戏进程在跑、但它**所有可见窗口的标题都是 `Message`**（引擎崩溃框的标题）→ 认定是上一局崩溃的残留：日志写 `上一局崩溃了，只剩 Fatal error 窗口，先清掉它 pid=… windows=Message reports=…`，`TerminateProcess` 清掉，然后照常启动新游戏、挂 worker。双击一次就恢复，不用先去点"确定"。
- 进程在跑但一个窗口都没有时只记 `游戏进程在跑但还没有窗口（可能还在加载）`，**不动它**——避免把正在加载的游戏误杀。
- 崩溃报告仍在 `runtime\test-client\SFGame\Logs\`（`UE3AutoReportDump*.txt` + `unreal-*.dmp`），清进程不删报告。
