# 01 · 原理：游戏怎么算这一枪，我们从哪里拿到它

## 1. 现象与起点

游戏里子弹打在尸体上会飙血、会留下弹孔，但**尸体纹丝不动**；而打在场景里的台球、桶这类刚体道具上，它们会被打飞。

这不是引擎的布娃娃坏了——把尸体从高处推下去、被爆炸波及，布娃娃都正常。差别在于"子弹命中"这条路径。

## 2. 游戏内部的命中链

`SFWeap_Bullet.ProcessInstantHitSub`（脚本，2085 字节）在命中时会依次调用：

```
GetHitBoneNameforDEDIserver   读命中骨骼（游戏自己解析的）
CheckHeadShot / IsCriticalHeadShot / GetHitIncidenceAngle   判断爆头、入射角
CheckCriticalShot / GetBodyPartByBoneName / AdjustDamageForInstant   伤害修正
TakeDamageForLocalPawn / TakeDamage                        结算伤害
```

也就是说：**命中骨骼、入射角、部位**这些判定游戏本来就有，而且比外部射线猜测精确得多。

伤害结算走到 `SFPawn.TakeDamage`，它把动量交给 `HandleMomentum(Momentum, HitLocation, HitInfo, DamageType)`。问题在下一层：

```text
SFPawn.HandleMomentum   脚本体只有 `0b 04 0b 53`
                        （Nothing / Return / Nothing / EndOfScript）
```

**这个函数是空的**。引擎算出了冲量，交给它，它什么也没做就返回了。台球是 `SFKActorNoSync`，走引擎 `bDamageAppliesImpulse` 的刚体路径，所以飞出去；角色走的是这条被掏空的脚本路径，所以不动。

结论：游戏并没有"拒绝"鞭尸，它只是把这段逻辑留空了。我们要做的就是补上这一步——在正确的时机、用正确的着力点和方向，替它调用一次 `AddImpulse`。

## 3. 为什么不用"射线 + 骨骼距离"

第一版就是这么做的：从相机沿视线发一条射线，找最近的骨骼，距离小于阈值就算命中，再施加冲量。结果是两类错误同时出现：

| 现象 | 原因 |
| --- | --- |
| 打尸体旁边的地面/墙，尸体也会动 | 射线没有遮挡判断，穿过地面继续飞到尸体身上 |
| 必须用很"苛刻"的角度才推得动 | 门槛要求射线进入骨骼体积的 80%，擦着轮廓打（真实命中）反被判成 miss |
| 打手、打脚几乎不触发 | 末端骨骼细，几何近似误差比体积还大 |
| 枪响到尸体动有明显延迟 | 射线要在 Python 侧算 70 根骨 + 胶囊；早期版本还在开火后 `sleep(0.35)` 等位移 |

引擎自己的 `Trace` / `FastTrace` 通过桥调用时**永远返回"没碰到"**（参数回填正确，返回值恒为 0，包括垂直向下 4 万单位穿过地板），所以拿不到官方的命中点。命中特效、decal、弹着 actor 也都试过：这一版根本没有实例化（详见 `docs/02` 的"已排除的信号"）。

## 4. 真正的答案：武器自己记着每一枪打中了谁

`ASFWeap_Bullet` 上有一个 `RifleHitResult` 结构（`HitResult`，偏移 `0xC90`），里面是三个数组：

| 偏移 | 字段 | 内容 |
| --- | --- | --- |
| `0xC90` | `ImpactInfos` | `TArray<FImpactInfo>`，**按顺序**记录这一枪打中的所有东西 |
| `0xC9C` | `PenetrationInfos` | 穿透后的穿出点 |
| `0xCA8` | `DamageScale` | 每条命中对应的伤害衰减 |

每条 `FImpactInfo` 80 字节，其中前 52 字节正是我们要的：

```
+0   AActor* HitActor      打中的 actor（尸体就是 SFCPawn_N）
+4   FVector HitLocation   命中点的世界坐标
+16  FVector HitNormal     表面法线
+28  FVector RayDir        子弹方向（单位向量）
+40  FVector StartTrace    射线起点
```

**每开一枪，游戏自己重写这三张表。** 所以：

- 打尸体 → 表里第一项就是尸体的 actor，坐标就是弹着点；
- 打墙/地面 → 表里只有墙/地面，没有尸体（假阳性从物理上不可能）；
- 侧面打头、打手指 → 游戏已经算好了骨骼与命中点（角度问题自动消失）；
- 我们不用做任何几何运算，只需一次 12 字节的读 + 一次数组读（微秒级）。

这就是"用游戏自己的判定"：我们不再是猜，而是读答案。

## 5. 数据流

```
玩家开枪
   │
   ├─ 游戏：ProcessInstantHitSub → 伤害/特效 → 重写 HitResult.ImpactInfos
   │
   └─ 补丁（每 4ms 轮询）
         ├─ 读本地玩家武器 (PlayerController.Pawn.Weapon)
         ├─ 读 AmmoCountInMgz，比上一轮少 1 ⇒ 刚打出一发
         ├─ 读 ImpactInfos / PenetrationInfos（每条 80 字节）
         ├─ 对每条 HitActor：Health<=0 且 Mesh 是 SkeletalMeshComponent ⇒ 尸体
         ├─ 取 HitLocation、RayDir → 冲量 = 归一化方向 × strength
         ├─ 调 Engine.PrimitiveComponent.AddImpulse(mesh, impulse, none, hitLocation, false)
         └─ 0.35s 后读 mesh 的 LocalToWorld 平移，记录实际位移 moved(cm)
```

`AddImpulse` 通过游戏自带的桥在主线程执行，一次调用约 20ms（含跨线程往返）。从枪响到尸体受力，实测通常在同一帧到两帧内。

## 6. 关于"空函数"的边界

- 本补丁**不修改** `HandleMomentum` 或任何脚本，也不改游戏文件；它是在外部补一次冲量。
- 因此它只影响"看起来"：伤害、血量、AI、命中判定仍然是游戏原样。
- 只对本地玩家手上的枪有效（读的是自己武器的 `HitResult`）。队友/敌人的枪不经过这个结构。

## 7. 被否掉的方案（留档，避免重复踩坑）

| 方案 | 为什么不行 |
| --- | --- |
| `Engine.Actor.Trace` / `FastTrace` 经桥调用 | 恒返回 0，连垂直穿地板都"没碰到" |
| `SFWeap_Bullet.FireEndTrace(bIsTest=True)` | 返回 `StartTrace + Dir*100000`，即"什么都没打中"的硬上限 |
| 新 actor（弹着、曳光、血） | 交火 25 秒内关卡 actor 表零新增 |
| Decal / DecalComponent | 这一版 `ActiveDecals` 恒 0，8 个实例全零，系统未启用 |
| 全 GObjects 扫描找新特效对象 | 18 万对象、单次 5.2 秒，每发子弹都扫不现实 |
| 读 `SFPawn.LastTakeHitInfo` | 尸体被子弹打中时该字段**不更新**（实测 7 发无变化） |
| Hook `ProcessEvent` 抓命中 | 命中/受击脚本不经过 `ProcessEvent`，抓不到 |
| 骨骼距离/胶囊几何 | 见第 3 节，假阳性与漏判同时存在 |

## 8. 弓 / 飞斧 / 投掷刀：投射物本身就是"命中记录"（1.1.0，1.3.0 重写判据）

枪能靠 `HitResult` 是因为子弹是**瞬时**判定、没有实体。弓和投掷武器相反：它们有真实飞行的
actor（实测类名 `SFCProjectileBowArrow`、`SFCProjectileTomahawk`），关卡 actor 表里看得到。

实测寿命：对着尸体投出的飞斧 **0.87~0.89 秒**被销毁；落在空地上的那一把活了 **16.9 秒**，
模型一直留着。也就是说——命中 = 投掷物在尸体旁边被销毁；落地 = 模型留着、对象继续存在。

所以判据是：`gone` 时只看**最后 4 个采样点**（约 4 ms 一个）与尸体骨骼的最近距离，
不超过 `projectile_radius`（默认 **70 cm**）才算命中，取该点作着力点、末速度作方向。

半径的来历（三个实测数字，改之前先重测）：

| 情况 | 销毁点离最近骨骼 | 结论 |
| --- | --- | --- |
| 贴到 2 m 内直击 | 1.9 / 6.7 / 10.5 / 12.7 / 12.9 cm | 必须算命中 |
| 站远一点、准星压在尸体上投 | **60.9 / 60.9 / 63.9 cm** | 必须算命中 |
| 对着空地投 | 1522 / 1550 / 1645 / 1719 cm | 必须不算 |

60~64 cm 不是"擦身"：飞斧模型在飞的时候一直旋转，模型比骨球大一圈，重心投影和最近骨骼之间
本来就有距离。45 cm 会把正常距离的真实命中全部漏掉（1.8.1 实测三次全 miss）。

关键点：**不能看整条折线**。飞斧穿透尸体后继续飞，整条折线上最近的点可能是中段的 1.9 cm，
也可能只是擦身的 33 cm —— 只有"在附近死掉"才是游戏自己的裁决。

`SFProj_Arrow.bStucked`（0x404）、`AttachedTo`（0x408）、`VictimActor`（0x318）**都不能**当判据：
飞行途中 `bStucked` 会随机翻 true，另两个全程 null。

#### 8.00000 两个必修的 bug（1.8.1）

**① 投掷物在检测循环里隐形。** `Pawns.kind()` 按 actor 地址缓存类名，而 actor 内存会被复用：
新投掷物拿到刚释放的旧地址时，缓存里还是上一个对象的名字，`startswith` 判断永不成立 —— 探针
能看到完整折线（69 个点、最近 33 cm），worker 却一个事件都没有。修法：`poll()` 记下上一轮的
地址集合 `self.slots`，对**这一轮新出现**的地址先把类名缓存丢掉再读。

**② 站在尸体上投掷会被误判成命中。** 出生点在玩家手里，离脚下尸体的骨骼只有 30 cm。1.8.1 用
"起飞后 0.12 s 内的采样不算"来挡，但按 24 m/s 算那是近 3 米的飞行 —— 近距离投掷的**整个接触段**
都被吞掉，冲量要等飞斧落地停稳（约 0.8 s）才施加，体感就是"投掷延迟很高"。1.8.3 改成：

* `projectile_grace`（默认 0.02 s）只丢"还在手里"的那一个采样；
* 头 `projectile_launch`（默认 0.15 s）内只认**前方**的尸体：要求 `(骨骼 − 出手点) · 线段方向 > 0`。
  站尸体上投掷时脚下的骨头在正下方，点积约为 0（甚至在身后为负），因此被排除；而前方 60 cm
  的尸体点积就是 +60，正常算命中。

结果：近距离投掷从"手柄之后约 0.8 s"变成"接触当帧"（实测 `age` 0.02~0.05 s）。

#### 8.0000 边飞边判，去掉一秒延迟（1.7.0）

1.6.x 在 `gone` 时才算账，而飞斧从投出到被释放要 1.0~1.3 秒，所以冲量总是晚一拍。现在 `Projectiles.poll()` 每追加一个采样点就发 `('move', entry)`，`arrows()` 立刻用**最新那一段线段**去比骨骼：命中当帧就 `AddImpulse`。延迟从"整段飞行"降到"一个轮询周期 + 一次桥调用（约 21 ms）"。

同时投掷力度 700 → 900（`max_impulse` 1400）：其余武器仍用 700。

### 8.000 回到整条轨迹 + 骨骼缓存（1.6.0）

1.5.0 假设"命中即隐藏"，实测推翻：`bHidden` 翻转时投掷物离最近骨骼 **1522~1719 cm**，即它是在飞出地图时被隐藏的。飞斧不把尸体当障碍，穿透后继续飞，游戏对它是否碰过尸体**不留下任何记录**。

所以判据只能是几何的，但要把几何算准：

1. `corpse_meshes()` 缓存骨骼 250 ms（`BONE_TTL`）——原来每个采样点都重读 6 具尸体 × 70 根骨头，循环只有几 Hz；
2. `Projectiles(samples=512)`——按 4 ms 采样可覆盖 2 秒飞行，不会把命中段挤掉；
3. `path_hit()` 用**线段**到骨骼的距离（不是采样点），采样稀疏也不会漏；
4. 半径 `projectile_radius` 默认 70 cm（1.6.1 由 60 调高：实测唯一漏判的一次是 63.2 cm），命中点取线段上最近的那一点。

### 8.00 判据换成 bHidden 翻转（1.5.0）

1.4.0 的"寿命 + 距离"仍然时灵时不灵（同一批投掷里，轨迹离骨骼 15~131 cm 全都有）。原因是采样间隔：投掷物每帧飞几十厘米，靠点云猜"擦过"本身就不可靠。

改用游戏自己的动作：`Engine.Actor.bHidden`（偏移 **0xB0**、掩码 **0x2**）。命中尸体时游戏在接触的那一帧把模型隐藏，落地则不隐藏。所以：

1. 每个投影物每轮读一次 0xB0；
2. 由 0 变 1 的那一轮，把当轮读到的坐标当作命中点；
3. 命中点到最近尸体骨骼 ≤ `projectile_radius`（默认 60 cm）才施加冲量，否则记 `projectile-miss`。

这样"打中/没打中"由游戏自己决定，我们只做几何归属。`projectile_lifetime` 只作为兜底（某些情况下对象被直接释放、没翻 bHidden）。

### 8.0 改用"寿命 + 整条轨迹"（1.4.0）

1.3.0 只看"销毁点离骨骼多远"，在真机上仍然漏判。补测得到的事实：

| 投掷结果 | 消失用时 | 消失位置 | 轨迹离骨骼最近距离 |
| --- | --- | --- | --- |
| 打中尸体（3 次） | 0.868 / 0.884 / 0.883 s | 空中 | — |
| 打中尸体（复测） | 1.078 s | 空中 z≈9979 | 35.99 cm |
| 打地面（对照） | 16.896 / 17.078 s 才被清理 | 落点不动 | 52.98 cm |

结论：**命中 = 投掷物在空中被立刻销毁；没命中 = 落地后模型留着、要十几秒才被清理。**
距离不能当主判据（35.99 对 52.98，只差 17 cm），现在只用来排除"从旁边几十厘米外飞过去"的情况（阈值 60 cm）。
`config.json` 的两个键：`projectile_lifetime`（默认 2.0 秒）、`projectile_radius`（默认 60 cm）。

## 8.1 1.2.0 为什么没效果（教训）

1.2.0 用的是"存活时间 < 3 秒 + **整条折线**离骨骼 ≤ 14 cm"，两头都错：

- 14 cm 是拿贴脸直击标定的，正常距离投掷时最后一帧常在 20~30 cm ⇒ 真命中被漏掉；
- 擦身 33~39 cm 的那几次同样短命 ⇒ 本应排除的却进不了判定（因为 14 cm 又太紧）。

1.3.0 换成"销毁点 + 45 cm"：只测死亡前的几个点，既容得下采样误差，也不会把"飞过去"当命中。
另外尸体躺在地上，直接用投射物速度方向（多半朝下）推会把尸体压进地板（`settled.moved` 只有
2~8 cm），`slide()` 只保留水平朝向并加 0.08 抬升，尸体才会在地上滑出去。

> 踩过的坑一：`try: self.melee(); self.arrows()` 这种写法，近战读取抛一次 `OSError` 就整段跳过，
> 结果是弓能工作、飞斧一次都没被检测到。两个检测必须各自 try。
>
> 踩过的坑二：对象被释放后还会在关卡 actor 表里留一帧，位置读出来是垃圾（z≈9970）。
> `projectiles.poll()` 用"单帧位移 > 400 单位"把这种采样丢掉。

## 9. 近战：两个状态位（1.1.0，1.8.2 补左键挥击）

F 键挥击在这个构建里是原生代码直接结算的：`SFWeap_Melee.DamagedActors`/`ImpactList` 只是函数
**参数**，`SFWeap_MeleeSwing` 这个本该记账的类在挥刀时**不产生实例**（全表只有 CDO）。

唯一稳定可读的信号是 `SFPawn_Player.DoingExigencyAttack`（BoolProperty，偏移 `0xED8`，掩码 `0x8`）：
挥击期间为 1，实测 3 次挥刀全部抓到上升沿。拿不到"砍到了谁"，所以用几何补：相机位置到
**最近尸体骨骼**的距离 ≤ `melee_reach`（默认 130 cm）就算命中。

**投掷武器的左键近战不置这个位。** 它和开枪、投掷共用 `SFWeapon.BurstFireCount`（IntProperty，
偏移 `0xBE0`）：动作开始 0 → -1，结束回 0。实测飞斧左键近战三次脉冲各约 0.79 s **弹药不变**，
而同一把飞斧投掷是脉冲 + `AmmoCountInMgz` 1→0，M4 射击是脉冲 + 30→29（只有 0.09 s）。
所以判据是下面两条同时成立：

1. `BurstFireCount` 出现上升沿；
2. 等 `swing_delay`（默认 0.3 s）后弹药**没**减少 —— 减少了就说明是开枪或投掷，丢弃。

一次挥击只推一次（`last_strike` 0.45 s 去重），因为 F 键那条路可能同时被触发。

为什么必须用骨骼：实测站在尸体上挥刀时，尸体 actor 原点到准星的距离是 10.8，但
`along = -0.9`、`cosine = -0.081`，也就是原点在视线背后；只有骨骼坐标能表达"脚下这具尸体"。

## 10. 拖拽：GMod 式"冲量伺服"（1.9.0 → 1.9.2 重写）

想把尸体拖着走，第一反应是"每帧把它的位置设到玩家前面"。这条路在本构建里走不通，原因有两个：

1. **没有可用的速度/位置接口**。`Engine.PrimitiveComponent.AddImpulse(Impulse, Position, BoneName, bVelChange)`
   在参数表里确实有 `bVelChange`，但实测传 `True` 与传 `False` 的位移一模一样 —— 这个构建**忽略它**
   （`punch.py` 顶上的注释就是为这事写的）。`AddForce` 连 `bAccelChange` 都没有这个参数。
   `Engine.RB_Handle.SetLocation` 存在，但布娃娃的 RB_Handle 不在 `SkeletalMeshComponent` 的已知
   成员里，拿不到句柄。`Actor.SetLocation` 只能搬 actor 原点，布娃娃的骨头由物理资产自己跟着走，
   搬过去下一秒就被关节拉回原处 —— 实测尸体只会"抽一下"。
2. **玩家的意图是"拽"，不是"瞬移"**。所以做法是周期性读一次被抓住的那根骨头的世界坐标，算出它离
   目标点还差多少，再发**一个** `AddImpulse`。骨头被推、关节带着其余身体跟上，尸体于是会晃、会撞墙、
   会卡在门框上——这正是"拖"该有的样子。

### 10.1 第一版为什么"鬼畜"，又为什么抬头不跟（1.9.0 的问题）

1.9.0 的伺服是 `push = clamp(drag_mass × (min(drag_gain×距离差, drag_speed) − 沿目标方向速度), ±1200)`，
**每 4 ms 轮询都发一次**。140 cm 的误差下这一项每一轮都顶到 1200 的上限：等于给物理引擎喂了一个
250 Hz 的饱和方波，引擎每次积分都被打断，视觉上就是抽成一片。同一版的目标点是
"玩家脚点 + **压平**的水平朝向 × 140 cm，z 固定为抓取时的高度"，所以抬头时目标点根本不上升，
尸体当然不跟。

### 10.2 现在的控制器

- **目标点**：`eye + forward × drag_distance`（`drag_distance` 默认 200 cm，三维，抬头即抬）。
- **控制频率** `drag_hz = 60`：两次冲量之间让物理自己积分，单次冲量上限降到 900。
- **临界阻尼 PD**（在速度域，输出的是"想要的 Δv"）：
  `accel = drag_kp × 误差 − drag_kd × 速度`，`kd = 2√kp`（默认 `kp 20`、`kd 9`）。
  速度由相邻两次采样的差分得到，再过 0.5/0.5 低通——60 Hz 差分出来的噪声如果直接进阻尼项，
  本身就会变成可见的抖动。
- **重力补偿**：`+ 980 × drag_gravity`（默认 1.0），并且加在**限速之后**，否则 `drag_max_speed`
  会把补偿也一起削掉，尸体会慢慢往下沉。
- **质量在线学习**：`m ≈ |J| / |Δv|`（用上一 tick 的冲量与这一 tick 的速度变化），
  `Δv < 5 cm/s` 视为被地面/墙挡住、不学，样本还必须"朝推的方向动"（`dot(ΔJ, Δv) ≥ 0.7`），
  否则那是关节或接触在动、不是冲量在动。单次最多改 15%，再指数平滑 0.9/0.1，初值 `drag_mass 20`，
  夹在 1~400 kg。小腿和骨盆需要差好几倍的冲量，写死一个数必然一边过冲一边拖不动；
  而一次接触样本就能把 20 kg 估成 3 kg，增益随之翻三倍——"单次最多 15%"就是为这个加的。
- **抓骨盆，不抓准星那根骨**：冲量打在什么骨头上，身体就绕什么骨头转。抓头或手时几乎全部冲量变成
  力矩：实测抓 `Bip01-Head` 时尸体 1.9 秒被甩出 714 cm 直接触发 `too-far`。骨盆在质心上，
  同样的冲量变成纯平移。骨骼名按 `GetBoneName` 逐个查到 `Bip01-Pelvis` 为止，找到后把
  索引写进 `self.core` 缓存，之后每次抓只用一次 `GetBoneName` 复核（骨骼名对所有同类尸体都一样，
  缓存可以跨尸体复用）。实测抓骨盆：误差 30~60 cm、单次冲量 130~430、抬头 2.5 秒内尸体跟着升高 265 cm。
- **松手**：偏离超过 `drag_break`（600 cm）**持续 0.3 s** 才松，避免一瞬间的碰撞把抓取打断。
- **死骨兜底**：手指/脚趾常常没有自己的物理体，冲量打上去骨头一动不动，伺服会一直满力推（1.9.0 的日志里 `moved 0.0 / ticks 60 / calls 60` 就是这样）。0.2 秒内位移不到 1 cm 就改成推根节点（`BoneName` 留空，整具尸体动），记 `drag-rebone`。

三个实测数字决定了默认值：

| 量 | 实测 | 默认值 |
| --- | --- | --- |
| 抓住的骨头与玩家脚点的高度差 | `Bip01-L-Calf` 11.1 cm（小腿本来就在这个高度） | 抓取时记 `lift` 写进日志，目标点用相机而不是脚点 |
| 单次 `AddImpulse` 能让骨头移动的量 | 1200 冲量 ≈ 250 Hz 下每 tick 都到上限 ⇒ 抽搐 | `drag_impulse 900` + 60 Hz |
| 拖 6 秒的实际位移 | `moved 176.4 cm / path 10659.8 cm`（1.9.0 的峰值，伴随上下振荡） | 新控制器以 `error`（松手时的残余距离）作为调参依据 |

按键同理不能猜：`GetAsyncKeyState(VK_E)` 能读，但分不清"在游戏里按 E"和"在聊天框里打 e"。
`SFPlayerController.bPressingUsedKey`（BoolProperty，偏移 `0x690`，掩码 `0x40`）是游戏自己解析交互键
之后的状态，**跟着改键走**，且输入被 `bIgnoreInput`（同字掩码 `0x400`）吞掉时它不会置位。
所以按键优先走它，`GetAsyncKeyState` 只是"偏移读不到时的兜底"，并且一旦游戏状态位工作过
（`native_ok`），后续就再也不看 OS 键盘 —— 否则打字、切窗口都会把尸体拽一下。

单击/再单击的切换放在 `Worker.toggle_drag()` 里，抓取判定复用 §9 的"最近尸体骨骼"几何，
只是半径放大到 `drag_reach`（默认 300 cm）。抓不到时记 `drag-none` 并带上 `near`（最近骨骼距离），
这样"按了没反应"能一眼看出是超距还是根本没尸体。

## 10. 被证伪的第四条路：不用桥、直接写刚体速度（2026-10-26 实测）

背景：R6 版本的人机 AI 用同一个 `0x6008D0` 入口和同一个 `remote+0x1000` 命令块，但用的是**批量协议**
（`state+4` = 调用条数，`state+0x100` = 384 字节的调用记录数组）。本 mod 的单调用块与它不兼容：
一个进程只能有一个钩子，谁先装谁独占，后装的一方要么装不上、要么把对方的块写坏。所以试过一条
"完全不碰钩子"的路——纯数据写刚体速度。`tools/physics_probe.py` 是为此写的探针。

反射链本身是通的（全部脚本可见，无需硬编码偏移）：

```
Pawn.Mesh -> SkeletalMeshComponent.PhysicsAssetInstance(0x218)
          -> PhysicsAssetInstance.Bodies(0x44) -> RB_BodyInstance[n]
             RB_BodyInstance.BodyData(0x60) / Velocity(0x44) / PreviousVelocity(0x50)
PhysicsAsset.BodySetup(0x40) -> RB_BodySetup.BoneName(0x84)     # 骨名映射
```

但实测结论是**写不动**：

| 观察 | 数值 |
| --- | --- |
| `RB_BodyInstance.BodyData` 的宽度 | **4 字节** —— 指向原生 `FBodyInstance` 的指针 |
| 一发 `AddImpulse` 后的 `Velocity` | `(0,0,0)` → `(-21.52, 71.71, 87.88)`，且**只有 root body** |
| 真实速度三元组的位置（12 帧投票） | 原生结构某个一级指针的 `+0x44` / `+0x50` 两处 |
| 往那两处写 `+400` 的 z 速度后，引擎镜像是否采纳 | **3/3 全部 false** |

原因：那两处是**引擎每帧从 PhysX 刷回来的镜像**，写回去会被下一个物理步覆盖；而已经睡着的刚体
（实测 `frames_asleep: 488`）还需要 `wakeUp` 才会重新参与模拟，那是函数调用、不是数据写。
**纯数据写不可能驱动布娃娃**。继续挖 PhysX 内部的睡眠标志位收益低、风险高（写坏物理状态可能崩进程），已停。

因此要在 R6 的 AI 模式下共存，只剩三条路：让 R6 的 worker 不启动（`--no-ai-worker`）、
本 mod 检测到外部桥就明确退出、或改成说 R6 的批量协议并自行做互斥。
